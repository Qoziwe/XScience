# XScience — бэкенд (Flask)

Серверная часть панели оценки пожарной обстановки. Реализует API из
`FUNCTIONAL_SPEC.md` §18: авторизация, анализы, сектора, состояние корабля,
отчёты, ИИ-модуль текстов, ML-модель риска, закон d² и фото пламени.
**Весь расчёт выполняет сервер** — клиент присылает только сырой вход §4.1 и
получает готовую запись §4.2 с баллами, вердиктом и текстами (§18.3).

Два разных ИИ в проекте, не путать:

| Что | Чем сделано | Влияет на вердикт |
| --- | --- | --- |
| Тексты отчёта и рекомендации (§2.2, §15) | языковая модель любого провайдера, фолбэк — правила §15 | **нет**, только проза |
| Прогноз риска и затухания (§17.1) | softmax-регрессия на наборе §19 | **нет**, вердикт даёт расчёт §14 |
| Признаки фото пламени (§17.3) | vision-модель того же слоя | **нет**, это наблюдение |

Баллы, уровни, вердикт и уверенность всегда считают детерминированные
правила §14. Модель их не видит как предмет спора: она получает их готовыми
и пишет только текст.

## Запуск

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate   # необязательно
pip install -r requirements.txt                      # Flask (+ argon2-cffi)
cp .env.example .env                                 # и поправить секреты
python3 seed.py                                      # демо-учётка demo/xscience-demo
python3 run.py                                       # http://127.0.0.1:5000
```

Порт **5000** — на него уже проксирует `frontend/vite.config.ts`. Дальше:

```bash
cd ../frontend && npm run dev      # http://localhost:5173, вход demo / xscience-demo / 123456
```

Клиент выбирает реализацию API переменной `VITE_API`: `http` (по умолчанию —
этот бэкенд) или `local` (расчёт в браузере, прототип без сервера).

## Проверка

```bash
cd backend && python3 -m unittest discover -s tests -t .   # 79 тестов
cd ../frontend && npm run e2e                              # реальный httpApi против живого сервера
```

- `tests/test_scoring.py` — контрольные примеры §23 (A–F) и пример агрегации
  корабля: те же числа, что в спецификации и в TS-версии.
- `tests/test_api.py` — эндпоинты, лимиты входа, идемпотентность, валидация,
  неизменяемость записей, документ отчёта.
- `tests/test_ai.py` — адаптеры провайдеров (через локальный фейковый сервер,
  без сети и ключей), валидация ответа модели, фолбэк на правила §15.
- `tests/test_models.py` — набор данных, проверки §17.1, обучение и прогноз,
  закон d².
- `tests/test_photos.py` — загрузка, проверка содержимого файла, разметка,
  распознавание.

`npm run e2e` требует поднятого сервера и пустой базы.

## ИИ-модуль: подключение любого провайдера

Провайдер выбирается конфигом, код не меняется. `XSCI_AI_PROVIDER`:

| Значение | Что подключает |
| --- | --- |
| `openai_compat` | любой OpenAI-совместимый шлюз: OpenRouter и другие роутеры, Groq, Together, DeepSeek, локальные Ollama / LM Studio / vLLM. Синонимы: `openai`, `openrouter`, `ollama`, `lmstudio`, `vllm`, `groq`, `together` |
| `anthropic` | Anthropic Messages API (синоним `claude`) |
| `google` | Google AI Studio / Gemini (синонимы `gemini`, `aistudio`, `googleai`) |
| `none` (по умолчанию) | ИИ выключен, тексты пишут правила §15 |

Минимальный набор: `XSCI_AI_PROVIDER`, `XSCI_AI_MODEL`, `XSCI_AI_API_KEY`
и `XSCI_AI_BASE_URL` (для OpenAI-совместимых). Пример — OpenRouter:

```bash
XSCI_AI_PROVIDER=openrouter
XSCI_AI_BASE_URL=https://openrouter.ai/api/v1
XSCI_AI_MODEL=<издатель>/<модель>
XSCI_AI_API_KEY=<ключ>
```

Полный список переменных, параметры под конкретное API
(`XSCI_AI_EXTRA_JSON`) и примеры для Anthropic, Google AI Studio и Ollama —
в `.env.example`. У каждой функции может быть свой провайдер и своя модель:
`XSCI_AI_TEXTS_*` и `XSCI_AI_VISION_*` переопределяют общие значения,
`XSCI_AI_TEXTS=0` / `XSCI_AI_VISION=0` выключают функцию. Что реально
настроено, видно в `GET /api/health` (ключи не отдаются).

Свой провайдер добавляется модулем в `app/services/ai/providers/` с функцией
`complete(system, parts, cfg)` и записью в `REGISTRY`.

### Как это устроено и почему так

- **Модель не считает и не оспаривает числа.** Она получает параметры,
  слагаемые баллов, вердикт и уверенность как факты и пишет только
  `summary`, `why`, `why_ext`, `rec_intro` и шаги рекомендаций. Нумерацию
  шагов ставит сервер.
- **Ответ проверяется.** Обязательные поля, длины, 2–8 шагов, лимиты на
  заголовок и описание. Непригодный ответ, таймаут, недоступный провайдер,
  отсутствие настроек — всё это не ошибка запроса: в запись идут
  детерминированные тексты §15, а поля `texts_source` (`llm` / `rules`) и
  `texts_model` честно говорят, чем написан отчёт. То же пишется в раздел
  «Ограничения» самого отчёта.
- **Отчёт не меняется задним числом.** Текст генерируется один раз при
  создании анализа и хранится вместе с ним (§15), поэтому повторное чтение
  отчёта не дёргает модель и не может дать другой результат.
- **Задержка.** Генерация идёт синхронно внутри `POST /api/analyses`;
  предел ожидания — `XSCI_AI_TIMEOUT_S` (25 с по умолчанию), после него
  работают правила. На клиенте это время показывается как «идёт расчёт» (§9.5).

## ML-модель риска и затухания (§17.1)

`GET /api/models/ml/readiness` считает четыре проверки §17.1 по текущему
набору и показывает состояние модели. `POST /api/models/ml/train` обучает
softmax-регрессию (чистый Python, без зависимостей) на двух целях —
`risk_level` и `extinction_probability`; признаки — one-hot материала,
гравитация и нормированные числовые поля. `POST /api/models/ml/predict`
отдаёт классы с вероятностями.

**Прогноз не подменяет вердикт** (§17.1): вердикт всегда из расчёта §14,
прогноз — отдельное справочное значение.

Набор данных: исходные 30 строк §19.2 (`dataset=v1`) не проходят три
проверки из четырёх, поэтому `scripts/gen_dataset.py` добавляет расширение
(`dataset=v2`, `app/data/dataset_extra.csv`): 90 строк, в которых
варьируются `risk_level` (все три класса) и `gravity`, а `data_source`
допустим по схеме §19.1.

```bash
python3 scripts/gen_dataset.py --rows 90 --seed 20261114   # результат детерминирован
```

**Честное ограничение, которое нельзя забывать:** метки расширения
посчитаны формулами §14, то есть набор остаётся `simulated`. Обученная
модель воспроизводит правила, а не независимые наблюдения, и доказательством
физики не является — это видно в ответах (`labels_are_rule_derived: true`)
и в примечании к обучению. На текущем наборе точность на отложенной
выборке — около 0.87 (risk_level) и 0.78 (extinction_probability). Чтобы
модель что-то добавляла к правилам, нужны измерения, а не пересчёт правил
(§19.3). Поля `flame_size_cm`, `flame_spread_rate_cm_s` и `expected_result`
в расширении пустые: правило для них не задано (§19.1), а выдумывать
значения в наборе данных нельзя.

Строки с `data_source` вне схемы §19.1 в обучение не идут — поэтому
проверка `data_source` в `readiness` остаётся непройденной (90 из 120),
а обучение при этом доступно: в `training_set` видно, сколько строк
исключено и почему.

## Фото пламени (§17.3)

`POST /api/photos` (multipart) принимает один снимок JPEG или PNG;
тип определяется по содержимому файла, а не по заголовку, предел размера —
`XSCI_PHOTO_MAX_MB` (8 МБ). Файлы лежат в `XSCI_PHOTO_DIR`
(`data/photos`, вне веб-корня) и отдаются только по сессии через
`GET /api/photos/{id}/file`.

`PATCH /api/photos/{id}` — разметка оператора по словарю §17.3
(размер / яркость / форма; пустое значение снимает выбор).
`POST /api/photos/{id}/recognize` — те же три признака от vision-модели;
значения вне словаря не принимаются, «пламени не видно» обнуляет признаки.
Разметка оператора и результат модели хранятся **раздельно**: распознавание
не затирает то, что поставил человек.

Признаки снимка — наблюдение: в расчёт риска и затухания они не входят
и на вердикт не влияют (§17.3).

## Безопасность (§6.5)

- Пароли: argon2id (`argon2-cffi`), при отсутствии пакета — scrypt из
  стандартной библиотеки. Обратимого шифрования нет.
- Второй фактор: TOTP, 6 цифр, окно ±1 шаг. Секрет печатает `seed.py`.
- Лимит пароля: 5 неудач → блокировка 30 с, считается и по логину, и по IP
  (скользящее окно длиной блокировки, отсчёт от последней неудачи).
- Лимит кода: 3 неудачи → сессия шага 1 аннулируется.
- Ответ и время ответа на «нет такого логина» и «неверный пароль» одинаковы:
  хеш проверяется всегда, ответ не короче `LOGIN_MIN_RESPONSE_S`.
- Сессия: cookie `HttpOnly; SameSite=Strict` (+`Secure` при
  `XSCI_ENV=production`), абсолютный срок 8 ч, бездействие 15 мин.
- Все попытки входа пишутся в `login_attempts`.
- Регистрации нет, учётки создаёт администратор через `seed.py`.

### Перед продом

1. `XSCI_ENV=production` — выключает debug и статический демо-код.
2. `XSCI_SECRET_KEY` и `XSCI_COOKIE_SECURE=1`, только HTTPS.
3. Удалить демо-учётку `demo` (§6.5) и завести реальные через `seed.py`.
4. Поставить `argon2-cffi`.
5. Запускать под WSGI-сервером (gunicorn/waitress) — `run.py` только для dev.
   При нескольких воркерах фоновый поток передачи отчётов должен работать
   в одном процессе: `XSCI_REPORT_WORKER=0` у воркеров и отдельный процесс,
   дёргающий `reports.flush_queue`, иначе отчёты будут помечаться наперегонки.

## Принятые решения по открытым вопросам (§24)

| Вопрос | Решение |
| --- | --- |
| 16.1 — включение границ диапазонов | как в §14.1, границы включаются; отражено в «Допущениях расчёта» |
| 16.16 — канал подтверждения отчёта | макет: очередь → `sent` через 2.5 с, статус в БД (переживает перезапуск, в отличие от прототипа) |
| 16.19 — срок актуальности анализа сектора | не ограничен: последний анализ сектора учитывается всегда (как в прототипе); когда появится регламент — фильтр по `created_at` в `/api/ship/status` |
| 16.21 — роли и права | только `operator`; роль хранится в `users.role`, проверок прав пока нет |
| 17.3 — привязка фото к анализу | `analysis_id` необязателен: передаётся при загрузке или позже через `PATCH`; признаки снимка в расчёт не входят |
| 19.1 — недопустимый `data_source` в наборе | строки v1 оставлены как есть (на них опирается вкладка «Данные»), но в обучение не идут; расширение использует `simulated` |

## Что не реализовано

- `/api/sensors/*` (§18.8) — датчиков нет, и спецификация оставляет формат
  открытым [ВОПРОС 16.17].
- `/api/reference` (§18.5) — клиент держит справочники у себя; эндпоинт
  нужен только если появится второй клиент.
- На клиенте не подключены: вкладка «Модели» (эндпоинты §17.1/§17.2 готовы,
  но UI ещё ходит в свои константы), загрузка фото (живёт в памяти страницы),
  кнопка «Принято» (есть `POST /api/analyses/{id}/ack`), защита маршрута
  `/console` сессией (§22).
